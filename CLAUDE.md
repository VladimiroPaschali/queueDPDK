# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Two DPDK applications whose throughput is measured while varying the number of RX queues polled per core (1 to 2048) and the queue-selection policy. The target hardware is an AMD Alveo U55N running a modified Open-NIC shell with the QDMA PMD. Comments are partly in Italian.

- `nf-chain/`: the paper's "NF chain", an ACL followed by a Count-Min Sketch and a NAT. The NAT code lives in `src/nat_*`, `state.*` and `utils/`. The ACL comes from l3fwd-acl and is driven by `rules/fw_10k` and `rules/rule_ipv6.db`.
- `mica/`: the paper's MICA key-value store. `ported-mica/` is the MICA table, and the workload alternates GET and SET.
- `common/qflow.h`: CLI options, validation and names of the policies, shared by both apps.
- `experiments/no-drop-zip.py`: zero-loss throughput (RFC2544 NDR) with TRex on another host (`STLClient(server="100.78.72.16")`). Traffic comes from the `zipf-profile.py` profile. After the NDR search the script keeps the same app process running, has TRex send at the NDR rate and takes `perf stat -C <lcores>` windows (plus system-wide IMC CAS counts for DRAM bytes), normalized by the packets TRex sent in each window. It disables turbo (`cpufreq/boost`) for the run, and `--resume` skips points already in the CSVs. `plot_ndr.py` plots throughput and the per-packet events against the queue count. The experiments `nf-chain-seq` and `mica-seq` give the bound of a perfect policy: `sequential-profile.py` sends the same Zipf flows one after the other (trains proportional to the Zipf weight, at least 32 packets, chained single-burst streams) on 1 queue, with TRex pinned to one core (`trex_core_mask`), since TRex splits a burst over its cores and would interleave the flows again; `nf-chain-seq-ring8192`/`mica-seq-ring8192` repeat it with `-d 8192`, the largest RX ring the QDMA accepts (its ring-size table goes up to 8193 entries, the completion ring is 2*n+1): on 1 queue the 1024-descriptor ring, not the processing, limits the zero-loss rate (sequential traffic is processed at 3.8-4.1 Mpps in overload but loses above ~2.95). `plot_bound.py` draws the 8192-ring run as the "theoretical max" line and round robin on 1 queue as "baseline" over the policies (into `plots/bound/`, leaving `plots/ndr/` alone). `pqos.py` collects LLC/memory-bandwidth data for the Discussion section.
- `starvation/`: nf-chain plus `src/qprobe.h`, which timestamps every poll, logs the packets marked by `experiments/starvation-profile.py` (field-engine seq on sampled Zipf flows, TRex latency trailer on probes and finite flows) and prints per-queue drain and service gaps. `experiments/starvation.py` runs the starvation/FCT campaign and `plot_starvation.py` plots it. TRex splits a field-engine variable across its 4 DP cores by interleaving (core j sends j, j+4, ...), so per-flow seq analysis groups by `seq % k`.
- `adaptive/`: single-core nf-chain that picks the number of active RX queues at runtime (`--adaptive`, see `src/adaptive.h`). All `-q` queues (a power of 2) are set up at startup. The app then rewrites the Open-NIC RSS mask register (`queues-1`, the first indirection-table entry that the patched `qdma_dev_reta_update` writes; `src/qdma_rss.c` computes its address from the PMD's private `func_id`, so the Makefile adds the QDMA driver's private include dirs) and polls only the active queues, draining the dropped ones after a shrink. The controller (`adaptive_epoch()`) doubles the queues when more than `--adaptive-backlog-high` percent of the full polls leave over half the ring waiting (the backlog is read in O(1) from the PMD's completion indexes, `qdma_rx_backlog()` in `src/qdma_rss.c`; on the FPGA this share tracks loss), and halves them below `--adaptive-backlog-low` percent or when the sweeps that found work have more than `--adaptive-empty-high` empty polls; a grow that raises cycles per packet without lowering the backlog is undone, and on flaps it keeps the larger count. Full polls alone are not a signal: Aggressive drains a backlog with full polls without losing anything. Every second the app prints `poll mix:` (empty and full polls of the active queues in the sweeps that found work, busy fraction, largest backlog), also without `--adaptive`. No multicore and no latency queue. `experiments/adaptive.py` runs it while TRex changes rate, skew, flows and packet size phase by phase (scenarios in `SCENARIOS`), compares it with fixed queue counts and logs a per-second timeline; `plot_adaptive.py` plots it. `experiments/adaptive_ndr.py` finds the zero-loss rate (its own binary search, with a warmup excluded from the measured run) of the controller (mode `signal`) and of every fixed queue count, for several numbers of flows; `plot_adaptive_ndr.py` places the controller on that queue sweep. Its trials measure steady traffic (counter differences after a warmup, flows started spread over 20 ms): every restart of the TRex traffic costs a transient, the first packet of every flow at once plus a loss that grows with rate and queue count (28k packets at 2.4 Mpps on 2048 queues), which a search that restarts the traffic every trial would count as loss. `adaptive/signal-policy.md` (Italian) describes the controller and the results. With 32 or more RX queues the NIC drops 25-60 packets per second whatever the rate (0.002-0.004% at 1-3 Mpps, none with 1-16 queues; real drops, they never arrive late), well below the 0.1% loss threshold that `adaptive_ndr.py` shares with the NdrBench search of `no-drop-zip.py` (`pdr=0.1`).
- `nf-chain-marco/`, `mica-marco/`: nf-chain and MICA on `../../dpdk20.11-marco`, a copy of the patched tree with a colleague's QDMA PMD changes: a per-lcore completion scratch (`qdma_cmpt_scratch`) instead of the 1 KB `cmpt_data` in every `qdma_rx_queue`, the hot `qdma_rx_queue` fields in one cache line, and `poll_hot`, dense arrays of every RX queue's write-back pidx pointer and completion cidx (also reset at queue start). `build/<app>-marco-pf` is `../<app>` plus a call to `rte_pmd_qdma_rx_queue_probe_many()` (the PMD's public API, as in the colleague's branch `qdma-strip-opennic`) before every sweep, used only as a prefetch: it reads every queue's write-back pidx through `poll_hot`, and the `for` of the sweep is unchanged (`probes ... ready queues/probe` every second). It includes the tree's `rte_pmd_qdma.h`, because the copy in `/usr/local/include` lacks the function. `build/<app>-marco-drv` is the unmodified `../<app>` sources on the same PMD. Experiments `{nf-chain,mica}-marco-{pf,drv}` (single core, as `nf-chain`/`mica`); `results_<app>-marco_*` come from a removed variant that polled only the queues the probe found non-empty (no gain over `-drv`); the `-iso` (current PMD re-measured, tag) and `-drv` points at skew 0.6 come from a first `experiments/run_marco_campaign.sh`, which now measures only `<app>-marco-pf` (baseline and aggressive, every queue count, skews 0.1/0.6/0.9); `plot_marco.py` compares the variants with `<app>-iso`.
- `locality/`: a separate CMS app plus `locality-bench.py` for Fig. 2 (distinct flows per burst). It does not use the policies.

## Build

```
cd nf-chain && make     # build/nf-chain
cd mica && make         # build/mica
cd starvation && make   # build/starvation
cd adaptive && make     # build/adaptive
cd nf-chain-marco && make  # build/nf-chain-marco-{pf,drv}, against ../../dpdk20.11-marco
cd mica-marco && make      # build/mica-marco-{pf,drv}, against ../../dpdk20.11-marco
```

The apps call QDMA PMD functions directly (`qdma_reg_read_usr`, `rte_pmd_qdma_*`). They can only be linked statically against the patched tree `../../dpdk-20.11` (`DPDK_LOCAL_PATH`). A `pkg-config` shared build fails at link time. There are no unit tests. Running on the FPGA is the only end-to-end check. Without the FPGA you can still smoke-test argument parsing: `sudo` is not needed with `--no-huge -m 256 --no-pci --vdev=net_null0 -l 0 -- <args>`. The run then crashes at the QDMA bitstream check, which is expected, and `stdbuf -oL` keeps the output.

## Policies and the polling loop

Policies are runtime options (see the table at the top of `common/qflow.h`): `--policy baseline|aggressive|penalty|aggressive+penalty`, `--penalty N`, `--latency-queue Q`, `--latency-period P` and `--multicore partitioned|shared`. In the code, Penalty is the variable `penalty` with the counters `queue_hit[]`, and Aggressive is `aggressive` with `max_loops`.

Each app has a single `poll_loop(const enum qflow_mode mode)` marked `__rte_always_inline`. It is instantiated three times (`main_loop_single`, `main_loop_partitioned`, `main_loop_shared`), so each multicore policy compiles to its own loop. The three modes intentionally keep the internals of the original separate programs, so the paper's numbers stay reproducible. Do not "unify" these differences without re-measuring:

- **Single core.** TX on queue 0 per burst, per-second `print_stats()`, and throughput measured after a 3 s warmup.
- **Multicore.** TX is batched (`TX_BATCH_SIZE`) on the lcore's own TX queue, with no per-second statistics.
- **Penalty counters.** Global on a single core, per lcore otherwise. Partitioned indexes them relative to its slice and keeps that index across a latency diversion.
- **nf-chain CMS.** 16×1M with a row-pointer table on a single core and in Shared, 16×65536 embedded in Partitioned, one sketch per lcore.
- **nf-chain NAT.** One table, one per lcore (Partitioned) or one per queue (Shared). Shared tables are locked and use 15-byte FlowIds (`FLOWID_PACKED_SIZE`). Multicore drops new flows when the table is full.
- **nf-chain mempool.** One per lcore in Partitioned, a single one otherwise.
- **mica.** Non-concurrent table with FIFO eviction on a single core. With more than one polling lcore the table is concurrent, and multicore uses an MTH threshold of 1.0. The single-core mempool omits the per-lcore cache term. Partitioned splits queues with `queues/lcores + extra` (nf-chain uses `queues*pos/lcores`).

The Python scripts parse the app output with regexes (`measured RX Throughput:`, `empty/sec (the poll read no packets)`, `pkts/burst`, and `ready` / `entering main loop` for startup). Keep those strings stable.

## Running

Use the FPGA at PCI `0000:16:00.1`, loading the PMD with `-d librte_net_qdma.so`. `ports.sh` rebinds the device and sets the Open-NIC registers (after a reboot 16:00.0 has memory decoding off, so it first sets it with `setpci`; a readback of `0xFFFFFFFF` means the writes were lost). Since 16 Oct 2026 the host boots with `isolcpus=0-11 nohz_full=0-11 rcu_nocbs=0-11 nosmt` (16 CPUs; the kernel keeps the tick on CPU 0, so `nohz_full` covers 1-11); the results measured before (the paper's, every `results_*` without `-iso`) ran with SMT on and no isolated cores. The EAL takes 20 1 GB pages from `/dev/hugepages`, remounted with `pagesize=1G`. nf-chain needs `-p 0x3 --config="(0,0,<lcore>)" --rule_ipv4=... --rule_ipv6=...`, and MICA takes only `-q`, `-d`, `-v` and the policy options. MICA allocates its table from 2 MB hugepages in `/mnt/huge`, which must be a `hugetlbfs` mount with `pagesize=2M` and about 4096 free 2 MB pages (otherwise it dies with SIGBUS at `initializing pages`). Neither the mount nor the pages survive a reboot. At startup both apps send `log2(queues)+1` packets carrying a magic value to clear leftover state. A packet with the `STOP123456789` magic stops nf-chain.

Experiments: `cd experiments && python3 no-drop-zip.py <experiment>...`. `--queues/--policies/--skews/--repetitions` override an experiment and `--tag` writes `results_<experiment><tag>_skew*`, so a subset never overwrites the main CSVs (without `--resume` the CSV of the folder is deleted). The experiment names are in the `EXPERIMENTS` dict (`nf-chain`, `mica`, `{nf-chain,mica}-{shared,partitioned}{2,4,8}`, `{nf-chain,mica}-seq{,-ring8192}`, `mica-ring256`). For the latency test (Fig. 6), run `nf-chain -q 64 --policy aggressive --latency-queue 27` while TRex on the other host measures latency.

Layout of `experiments/`: the scripts at the top; `results/ndr/results_<experiment>_skew*` (no-drop-zip.py, sequential runs included), `results/latency/`, `results/starvation/`, `results/adaptive/` (`calib.csv`, `ndr_v2/`, `timeline/`); `plots/ndr/`, `plots/bound/`, `plots/starvation/`, `plots/adaptive/<results folder>/`, `plots/marco/`, `plots/latency/` (`plot_latency.py`, which also draws zero-loss throughput against p99/max latency per queue count with the Pareto frontier); every plot script writes there, not into the results folders; `logs/` for the campaign logs. The scripts default to these folders. Results (`*.csv`), plots (`experiments/plots/`), `perf.data` and `build/` are gitignored.
